01 · Executive Summary

执行摘要

Hydra 是一个基于 Rust + Pingora 0.8 构建的高性能 LLM 路由网关，采用「纯领域核心 (hydra-core) + I/O 外壳 (hydra-server)」的两层架构，核心层零 I/O 依赖并有 CI 强制的依赖防火墙。代码工程质量出色：两个 crate 均开启 #![forbid(unsafe_code)]，生产代码中零 unwrap()/panic!/unsafe（全部限制在 #[cfg(test)] 内）。

基准性能测试（本地 10 核机器，使用线程化 mock 上游，未触达真实付费上游）显示：网关单请求开销约 0.3ms，峰值合成吞吐约 11,000 RPS（c=25，p99=4.39ms），限速下的稳定吞吐天花板约 3,500–4,000 RPS。内存表现极其出色——满载压力下 RSS 仅 18.6 → 65.4 MiB。

按 8 核 16G VPS 推算，预计可承载 6,000 RPS 合成峰值、2,000–3,000 路并发流式连接，内存占用远低于上限。

结论（补救后复评）：生产就绪。首轮评测中的全部 P0 与几乎全部 P1 已修复——provider 密钥 AES-256-GCM 落库加密（fail-closed 启动）、sqlx 编译期 query! 校验 + .sqlx 离线缓存、管理面不再返回明文（始终掩码）、mid-stream 错误指标补齐，并新增 per-provider 有界接纳队列（Envoy 模式，opt-in）。测试规模由 core 88→106、server 138→163 增长，热路径负载冒烟零回归（~10.5k RPS @ c=25）。剩余项均为非阻断的改进型条目（见风险登记表）。

03 · Architecture Overview

架构概览

CORE hydra-core 纯领域 · 零 I/O

仅依赖 serde / memchr / bytes / sha2。所有状态由注入的 Instant 驱动，无隐藏时钟。

SHELL hydra-server I/O 外壳

Pingora 代理外壳 + sqlx SQLite + reqwest + TLS + 管理面。

Terminate 模式请求生命周期

① 域名→租户解析
② 租户启用检查
③ 解析客户端 api-key
④ 外部鉴权缓存优先，命中跳过
⑤ 读取请求体硬上限 32MiB，超限 413
⑥ extract_model提取 model 字段
⑦ 预限流计数闸超限 429
⑧ 候选 + SWRRrouter::resolve + swrr::order 平滑加权轮询
⑨ 故障转移循环逐候选构造请求 → reqwest 发送 → SSE 流式回传；失败则 breaker.on_failure 并继续下一候选；返回 Ok(true) 使 Pingora 永不直连上游

核心组件

SWRR 负载均衡 熔断器 连续失败阈值 5 / 探活 10s 滑动窗口限流 请求数 + token 双维度 memchr 零拷贝 SSE 用量解析 (OpenAI/Anthropic/通用归一化) ArcSwap 热加载配置 SHA-256 鉴权缓存 allow 5min / deny 30s / 超时 2s / 默认 fail-closed

05 · Capacity Estimation

8 核 16G VPS 容量推算

推算方法学 · 本地基准：10 核 Apple Silicon（单线程较强）。目标 8C16G VPS：8 vCPU（AMD EPYC / Intel Xeon 服务器核，单线程约为本地的 0.6–0.8 倍）。CPU 密集型合成吞吐随「核数 × 单核速度」缩放。
指标本地实测8C16G VPS 推算说明
合成峰值吞吐11,056 RPS≈ 6,000–7,000 RPS按 8/10 核 × 0.7 单核系数
合成稳定吞吐3,500–4,000 RPS≈ 2,200–2,800 RPSp99 < 50ms 安全区
内存占用 (满载)65 MiB< 200 MiB (真实流式)16GB = 80x+ 余量，内存非瓶颈
并发流式连接—≈ 2,000–3,000真实 LLM 为 I/O 密集，CPU 在高并发成为上限
真实 LLM 业务吞吐 (5s/请求均时)—≈ 400–600 RPS (~24K–36K 请求/分钟)受上游 LLM 延迟主导，非网关

容量结论

在 8 核 16G VPS 上：内存完全不是瓶颈（占用 < 0.4%）。CPU 是主要约束：合成场景约 6K RPS 峰值、2.2–2.8K RPS 稳定；真实 LLM 流式业务（每请求 1–30s）下，网关单请求开销仅 ~0.3ms（相对 LLM 延迟可忽略），可支撑约 2,000–3,000 路并发流式连接。结论：单台 8C16G VPS 足以承载中大型 LLM 网关业务；如需更高吞吐，建议横向扩展 (多实例 + 共享 SQLite/外置 ClickHouse) 而非纵向加核。

08 · Methodology

评测方法学

01 代码评审

对两个 crate 全量静态走查（架构、错误处理、并发、持久化、安全、测试、运维），AST/grep 核验 panic/unwrap/unsafe 分布。

02 性能测试

release 构建 (cargo build --release --features server)，线程化 Python mock 上游 (预计算 SSE/JSON 响应)，oha 1.15 压测，预热鉴权缓存，隔离 mock 基线。未触达任何真实付费上游。

03 容量推算

基于实测数据按核数×单核速度系数外推至 8C16G，并区分合成场景与真实 LLM I/O 密集场景。

04 局限性

(a) 测试在本地 macOS 10 核进行，与生产 Linux 服务器内核/网络栈存在差异；(b) mock 上游为 Python，高并发区间部分衰减来自 mock；(c) 真实 LLM 上游延迟未模拟，流式连接数推算为理论值。

补救后复验 · 本轮补救后，所有静态/运行期验证（编译、clippy --all-targets、全量测试、at-rest 明文 grep=0、admin 4 路径 plaintext_leak=0、fail-closed 启动、负载零回归冒烟）均通过。
