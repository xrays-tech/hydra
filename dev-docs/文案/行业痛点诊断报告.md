# 行业痛点诊断报告

> 本报告是三套推广文案的前置分析。2026 年 8 月基于联网调研产出，所有引用均可经原文链接复核。

---

## 一、行业主流方案

LLM 网关这条赛道目前被 **LiteLLM**（Python/FastAPI，约 56K star）垄断，它是事实上的市占第一。它身后是一票「翻译型 / 转换型」代理：

- **OpenRouter**——托管 SaaS，闭源，每笔收 5.5% 过路费，所有流量必须经过它的云
- **Portkey**——TypeScript/Node，2026 年 5 月被 Palo Alto Networks 收购，开源前途未卜
- **Kong AI Gateway**——Lua 插件 + Go，企业版收费
- **Cloudflare AI Gateway**——SaaS，每秒限 500 条日志
- **Envoy AI Gateway**——Go + Envoy，2026 年 6 月 GA，**主打功能就是跨协议翻译**
- **Vercel AI Gateway**——SaaS，绑定 Vercel 平台

性能党以前还有个 **TensorZero**（Rust），**2026 年 6 月已 archive**。新冒出来的 Pingora 系（Tygress / FerroGate / AISIX / rolter / arcboxlabs）都很早期，星标个位数到几十，功能不全。

**一句话：能打的，要么是 Python（重且漏），要么是 SaaS（闭源且收税），要么是早期项目（不能上生产）。**

## 二、天下苦之久矣的痛点（最戳的两条）

### 痛点一：Python 网关是个吃内存的怪物，官方自己都认了

LiteLLM 的 GitHub issue 里，生产用户原话：

> *"one of my production servers went down when eventually it consumed almost 20GB of RAM alone, and that's being idle… totally crashed the server."*
> —— LiteLLM #12685（2025-07）

还有人贴了曲线：

> *"RSS climbs roughly linearly at ~0.7 GB/hour with no plateau — from ~0.7 GB just after a restart to ~9.6 GB in ~12.5h on an 11 GB VM. It never releases without a restart."*

官方文档直接认怂，**4GB 是地板不是目标**：

> *"4Gi is a floor rather than a target… glibc does not hand that memory back to the operating system afterwards. A pod's floor therefore ratchets up to its worst-ever write and stays there for the life of the worker."*
> —— LiteLLM Production Best Practices

HN 上有人直接开骂：

> *"We use LiteLLM and it is a bit of a dumpster fire… I'd sooner completely rewrite it in Golang/Rust or otherwise."*
> —— HN #45903485

**最重磅的第三方背书**：LiteLLM 自己在 **2026 年 6 月官宣全面 Rust 重写**，官方博客原话承认 *"CPU and memory climb with concurrency, and pods get OOM-killed"*，目标是把内存从 359MB 压到 32MB、吞吐提 15 倍。**龙头正花一整年重写，去变成 Hydra 出厂就是的样子。**

### 痛点二：转换 = 必然丢东西，丢的还是最贵的

所有「统一成 OpenAI 格式再转发」的网关，都在默默毁掉 Anthropic 最值钱的能力。**`input: {}` 祖传 bug** 是圈内梗：

> *"Model returns correct function.arguments (e.g. '{\"file_path\":\"test.py\"}'), but after litellm converts the response to Anthropic format, the tool_use.input becomes {} (empty dict)."*
> —— LiteLLM #27469（2026-05，v1.83.7 回归）

同一个 bug 横跨 Gemini / Ollama / Vertex / Bedrock / Qwen / glm-5.1，**在不同代码路径里修了至少 6 次**（#25601 / #25272 / #26636 + 内联修），每次「fixed」下次发版又回来。本质：**翻译层天生是 bug 工厂。**

更阴的是——你以为只是工具调用坏？**`cache_control` 在转成 OpenAI 线格式时被默默剥光**，缓存直接失效，整轮对话按全价 input 计费：

> *"Anthropic's caching infrastructure only honors cache_control on top-level system content blocks in the native anthropic_messages wire format — it ignores them on the OpenAI-compat path… the entire conversation context is billed at full input price on every turn… can be 10× more expensive than it should be."*

thinking block 也被拍平丢失 type identity。**连 Anthropic 自己官方文档都说**：

> *"For the best experience and access to Claude API full feature set (PDF processing, citations, thinking, and prompt caching), use the native Claude API."*

潜台词：别用那帮转换代理。

## 三、我们如何破局（Hydra 做对了什么）

针对上述两个核心痛点，Hydra 的对应解法：

| 行业通病 | Hydra 的解法 | 证据 |
|----------|--------------|------|
| Python 闲置吃 GB 级内存、OOM | **Rust + Cloudflare Pingora 原生**，满载 65 MiB，~0.3ms 网关开销 | `#![forbid(unsafe_code)]` 两 crate；0 unwrap/panic；baseline 相减测得开销 |
| OpenAI↔Anthropic 翻译层吃工具调用 / 吃缓存 | **双协议原生直通，零转换**：OpenAI 进→OpenAI 出，Anthropic 进→Anthropic 出，端到端同一格式 | `request_filter` 内终止请求，按客户端路径端到端保持同构 |
| SSE 流被 buffer / 中途失败变静默空 200 | Pingora 零缓冲流式回写；**中途失败显式报错**，不吞 | terminate-mode 架构，session 直写 SSE |
| 缓存 token 被当新 input 偷偷计费 | 细粒度计量：`prompt` / `completion` / `total` / `cached` 拆开 + `forward_latency_ms` + `ttft_ms` | OpenAI `prompt_tokens_details` + Anthropic `cache_read_input_tokens` 都吃 |
| 多租户共享一个 key、无租户级 TLS | **按租户鉴权 + 按租户 TLS（SNI 热更新）** + AES-256-GCM key 落库加密 | BoringSSL cert callback（rustls 不支持运行时回调，故弃用） |
| 失败重试砸死恢复中的供应商 | Nginx 同款 SWRR + 正经熔断器（dead-set + 后台探活） | 手撸 SWRR，因为 Pingora 自带的 LB 不带权重 |
| 故障转移重放成本高 | body 已全量缓存，`Bytes::clone` 引用计数 +1，**重放 O(1) 零 memcpy** | terminate-mode 副产品 |
| 你的 prompt 被网关 parse | `memchr` SIMD 扫 `"model"` / `"usage"` 关键字，**99% chunk 直接跳过**，只在 ~50 字节 usage 切片命中时反序列化 | 全程不 `serde_json::from_slice` 请求体 |

### 架构上的两个炫耀点

1. **终止模式（Terminate-in-Pingora）是行业共识**——我们调研了 8 个生产级 LLM 网关，没有一个用透传，全是终止模式。Hydra 的「战史」：初版用透传 + 只读首 chunk 提 model，遇到把 `model` 字段塞在 system/tools 大段前缀后面的客户端（如 Hermes agent）直接路由错误，被迫重写。终止模式上线后删了几百行框架 workaround 代码，hydra-core 零改动 83 测试全绿——这反过来证明了 **core / server 的 crate 依赖防火墙是焊死的**（core 的 `Cargo.toml` 物理上禁止依赖 tokio/pingora/sqlx/reqwest，CI 用 `cargo tree` 兜底）。

2. **龙头在追我们**——LiteLLM 的维护者在 HN 上明说参考的就是 Cloudflare Pingora（*"You can see other proxies (e.g. cloudflare's pingora) doing the same thing"*）。他们的 Rust 重写目标（sub-1ms 开销、32MB）就是 Hydra 今天的数字。

### 一句话定位

> **Hydra 是 2025–2026 LLM 网关赛道里，唯一同时具备「系统级语言数据面（Rust + Pingora）+ 双协议原生直通零转换 + 一等公民级多租户 TLS + 计量级用量分解」的项目——单二进制、65 MiB、零 panic、无 Postgres / K8s / SaaS 依赖。**
