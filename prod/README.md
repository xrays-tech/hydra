# Hydra — production deployment (single edge host)

This directory is a **complete, self-contained production deployment** for Hydra at the recorded
HEAD. Hydra *is* the edge proxy: a single app instance terminates plaintext on **:80** and
per-tenant TLS/SNI on **:443**, backed by PostgreSQL 16, Redis (shared data plane) and GreptimeDB
(usage sink) on a private network. There is **no nginx** and **no A/B pair**.

It is **not** the `environment/` developer stack: secrets are generated locally, data is
bind-mounted, and the release binary is mounted read-only rather than baked into the image.

## Topology

```
   host :80 (plaintext)          host :443 (per-tenant TLS/SNI)
            └───────────────┬───────────────┘
                            ▼
                       hydra-prod  (single edge instance; admin :8081)
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   postgres:16        redis:7          greptime/greptimedb:v1.3.0
        (network hydra-prod, 172.30.0.0/16; DNS by service name)
```

Host port mapping: `80→plaintext`, `443→TLS/SNI`, `${ADMIN_PORT:-18081}→admin`.

## Listeners (80/443)

* **`HYDRA_LISTEN=0.0.0.0:80`** — the always-on plaintext data-plane listener.
* **`HYDRA_TLS_LISTEN=0.0.0.0:443`** — a per-tenant TLS/SNI listener. Certificates are **not** files
  on disk: they are provisioned through the admin/config flow and stored in the relational DB, and
  selected by SNI. On a fresh deployment `:443` accepts TCP but **every TLS handshake fails until a
  tenant certificate is configured**; add one via the admin API/UI (`cert_pem`/`cert_key_pem`).
  `ops/health.sh` reports this distinction explicitly.
* **`0.0.0.0:8081`** — the admin API, published on the host as `${ADMIN_PORT:-18081}`. Bind it to
  loopback or firewall it: it is plaintext and its bearer token is the only authority.

Listener addresses live in the committed `prod/env/app.env`; secrets live in the gitignored
`prod/.env`.

## Build the binary

The **host build is the default** (native `cargo build --release`, then copied to
`prod/releases/hydra`):

```bash
prod/build/build-binary.sh              # host build (default)
prod/build/build-binary.sh --container  # pinned container build (prod/build/Dockerfile.builder)
```

Features compiled: `server,cluster-redis,usage-greptimedb,db-postgres`. Both invocations print the
highest `GLIBC_*` symbol the staged binary requires as a compatibility sanity check.

### glibc compatibility (measured 2026-11-11)

The release binary requires at most **`GLIBC_2.34`**. The runtime image is `ubuntu:24.04`, which
ships **glibc 2.39** (and 26.04 ships newer still), so a host-built or CI-built binary runs
directly in the runtime image — **no in-Ubuntu rebuild is needed**. The earlier container test
failures (`exit 139` / `exit 126`) were **Fedora SELinux bind-mount labelling**, not a glibc
mismatch; the `:z`/`:ro,z` mount options below fix that.

`--container` exists for a fully pinned build (Rust 1.98.0 + clang/llvm, cache-mounted target dir
and cargo registry) when the host toolchain is unavailable; it is not required for compatibility.

The pre-existing `target/release/hydra` may be **stale** (older builds predate the GreptimeDB usage
sink). Build once with the feature set above; do not reuse an old artifact for production.

## Start

**Pre-flight:** `docker compose -f prod/docker-compose.yml --env-file prod/.env config` must exit 0
(with no warnings about missing variables). It renders every mount, port and healthcheck without
starting containers, so run it after any edit to `docker-compose.yml`.

```bash
prod/ops/up.sh            # generates prod/.env if absent, prepares dirs, starts, health-checks
```

`ops/up.sh` refuses to start if `prod/releases/hydra` is missing. The app image
(`hydra-prod:latest`, built from `prod/app`) contains no binary — it is only the Ubuntu runtime.

## Operate

```bash
prod/ops/health.sh        # admin health on ${ADMIN_PORT:-18081} + TLS-listener report (needs .env)
prod/ops/down.sh          # stop (data preserved)
```

## Remote deploy

```bash
cp prod/deploy.env.example prod/deploy.env && chmod 600 prod/deploy.env
$EDITOR prod/deploy.env            # SERVER_HOST / SERVER_USER / SERVER_PASSWORD / REMOTE_DIR
prod/ops/deploy-remote.sh
```

`deploy-remote.sh` builds the app image locally, `docker save | ssh docker load`s it, rsyncs the
`prod/` tree (release binary included; `data/`, `deploy.env`, `*.tar` excluded), then runs
`ops/setup-dirs.sh` and `docker compose up -d` on the host.

## Secrets

`prod/.env` is generated by `ops/up.sh` when absent and is gitignored (`chmod 600`). Required keys
(see `.env.example` for the full list): `POSTGRES_*`, `REDIS_PASSWORD`, `HYDRA_DB_URL`,
`HYDRA_REDIS_URL`, `HYDRA_ADMIN_TOKEN` (`openssl rand -hex 32`), `HYDRA_ENCRYPTION_KEY`
(`openssl rand -base64 32` — losing it makes stored provider keys unreadable),
`HYDRA_USAGE_SINK`/`HYDRA_GREPTIMEDB_URL`, `ADMIN_PORT`.

`HYDRA_TRUSTED_PROXIES` is intentionally **unset**: Hydra is the edge and nothing sits in front of
it, so the socket peer address is authoritative and `X-Forwarded-For` is ignored. Set it only if
you later insert a trusted LB, otherwise leaving it unset is the safest configuration.

## Data and permissions

Bind mounts live under `prod/data/{postgres,redis,greptimedb,app}`; the release binary under
`prod/releases/hydra`. `ops/setup-dirs.sh` creates them and chowns the Postgres/Redis data dirs to
`999:999` and the app dir to `1000:1000` (see `prod/postgres/README.md` for why).

### Fedora / SELinux

Every relative bind mount in `docker-compose.yml` carries an SELinux relabel option: `:ro,z` for
read-only files (`releases/hydra`, `.env`, `redis.conf`, `greptimedb/config.toml`) and `:z` for
writable data directories (`data/*`). Without this, a SELinux-enforcing host (Fedora Workstation,
where this was measured) denies the container access to the host path and the process fails with
`SIGSEGV`/`exit 139` at exec — **not** a glibc issue. `:z` is accepted and harmless on hosts
without SELinux, so the same file works everywhere.

## Production hardening (not done in this baseline)

* **Postgres TLS is off.** The stack uses `sslmode=disable`/`HYDRA_DB_REQUIRE_TLS=0` because the
  database is only reachable on the private `hydra-prod` bridge. For a hardened deployment,
  enable Postgres TLS and set `sslmode=require` + `HYDRA_DB_REQUIRE_TLS=1`.
* **Redis/auth TLS is off.** Same private-network reasoning; Redis requires a password
  (`HYDRA_REDIS_REQUIRE_AUTH=1`) but speaks plaintext.
* **GreptimeDB has no auth and no TLS** in this config, and Hydra refuses `https://` for it
  (terminate TLS in a proxy if the store leaves the host).
* **The admin port (`${ADMIN_PORT:-18081}`) is plaintext and host-published.** Restrict it to
  loopback/an SSH tunnel or front it with an auth proxy; the bearer token is the only authority.
* **`:443` is only as good as its tenant certs.** Until a tenant certificate is provisioned in the
  DB config, the TLS listener accepts connections but completes no handshake.
